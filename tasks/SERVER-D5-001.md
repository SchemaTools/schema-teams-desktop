# SERVER-D5-001 — безопасное управление таймером из Desktop

Статус: задание для согласования и реализации ответственным за сервер Schema Teams.
Дата: 27.10.2026. Заказчик результата — разработчик Schema Teams Desktop, этап Д5.
Этот документ описывает предлагаемое изменение; перечисленные возможности ещё не реализованы.
Серверный разработчик работает в серверном репозитории, Desktop не изменяет.

## 1. Проверенная исходная версия и проблема

- Сервер: тег `0.11.2`, commit `f176f7635a50832b78ba570b56fd9ec5aa2813d4`.
- Проверенный текущий `stage/e13`: `62debe336c995f5f6e15ba54453a9380b1fe44dd`.
- На обоих refs договор Desktop — 1.1, blob `21bb1258ab9f82b05786e1ba11f58f7ec4fa56f6`.
- Файлы web desktop/timer и серверных timer routes совпадают с ранее проверенным
  `2589483a58b2c89be98db85ac1e7dc2782f995ad`; описанные ниже пробелы сохраняются.

Основные исходники для ответственного:
[договор](https://github.com/SchemaTools/schema-teams/blob/f176f7635a50832b78ba570b56fd9ec5aa2813d4/packages/shared/src/desktop-bridge.ts),
[модель БД](https://github.com/SchemaTools/schema-teams/blob/f176f7635a50832b78ba570b56fd9ec5aa2813d4/prisma/schema.prisma),

Сейчас `requestId` команды таймера не передаётся в API. Отложенный pause со старым
`at` может остановить уже продолженный на другом ПК таймер: сервер заменяет старое
время на «сейчас». Старое окно finish может записать строки таймера A и удалить уже
текущий таймер B. Команда stop игнорирует `at` и только открывает окно.

## 2. Состав изменения и границы

Нужны: проверки ожидаемого таймера, идемпотентность операций, подготовка finish
на время события, доставка пропущенного утреннего уведомления и метаданные бюро.
Приложение не получает пароль/токен: API по-прежнему вызывает страница Teams.

Сохранить существующие правила округления, проверки строк, прав и пересечений,
транзакционную запись, `/desktop/pick`, `/desktop/finish`, закрытие в полночь,
`workday.end`, `needsCheck` и серверное уведомление 08:00. Не переносить их в Desktop.
Не создавать второй таймер, отдельный учёт времени или новую систему уведомлений.

## 3. Договор 1.2 и обнаружение возможностей

Предлагается совместимое расширение `packages/shared/src/desktop-bridge.ts` до 1.2.
Старые поля и команды остаются. Основная версия 1 сохраняется: Д3/Д4 клиентов 1.1
продолжают работать. Новые автоматические действия разрешены только по capability.

Добавить авторизованный `GET /api/desktop/capabilities` и передавать результат в hello:
В hello сохраняются прежние user/serverVersion, добавляются capabilities/bureau/serverNow.
В примере ниже показаны только новые поля, а не замена полного hello.

```json
{"protocol":"1.2","capabilities":{"timerControl":2,"timerNoticeDelivery":1,"bureauTime":1},
 "bureau":{"timeZone":"Asia/Yekaterinburg","workday":{"end":1080}},"serverNow":"2026-10-27T12:00:00.000Z"}
```

Часовой пояс и конец дня — реальные настройки бюро, `end` в минутах от начала суток.
Они доступны только для чтения; Desktop не редактирует конец дня бюро.
Не объявлять `timerControl:2`, пока все операции ниже не защищены и не проверены.
Отсутствие capability не ломает чат, уведомления, пути и ручной интерфейс 1.1.

Расширить событие `timer` дополнительными полями; прежние значения не менять:

```json
{"state":"run","task":{"id":41,"mark":"АР1","title":"Объект А"},
 "startedAt":"2026-10-27T09:00:00.000Z","elapsedSec":10800,"reason":null,
 "timerId":314,"revision":7,"currentSegment":{"from":"2026-10-27T10:30:00.000Z"},
 "pausedAt":null,"serverNow":"2026-10-27T12:00:00.000Z"}
```

Подтверждённые типы БД: WorkTimer.id — Int/autoincrement, WorkTimer.version — Int.
`timerId:number` берётся из id; `revision:number` — из существующего version.
Сегменты сейчас содержат только `{from,to}`: отдельного segmentId нет и он не нужен.
Идентичность текущего сегмента — timerId + from, дополнительно защищённая revision.
У pause `currentSegment:null`, `pausedAt` — конец последнего закрытого сегмента.
В expected поле currentSegmentFrom имеет тип ISO string | null; у paused оно null.
У idle `timerId:null`, `revision:null`, `currentSegment:null`, `pausedAt:null`.
Сервер возвращает UTC ISO с миллисекундами и `serverNow`, в том числе при idle.
После каждой мутации новый снимок рассылается всем компьютерам пользователя.

## 4. Ожидаемое состояние и атомарная проверка

Новая команда Desktop захватывает expected и at в момент действия/блокировки:

```json
{"requestId":"7ce8b8a3-55ed-42e7-9749-563b6c75284b","action":"pause",
 "expected":{"timerId":314,"revision":7,"currentSegmentFrom":"2026-10-27T10:30:00.000Z"},
 "at":"2026-10-27T12:00:00.000Z","reason":"lock"}
```

Добавить expected и reason в общий договор и в web-валидацию команды timer.
Добавить action=`prepareFinish`: подготовить результат и вернуть ok, не открывая модальное окно.
Web передаёт их в API без замены на более свежий снимок, включая повтор после обрыва.
При отправке в API requestId становится заголовком `Idempotency-Key`.
Для защищённых timer-команд расширить ошибочный DesktopCommandResult полями code/retryable,
необязательными для старых команд. При timerControl:2 code обязателен: network_unavailable
может повторяться с тем же ключом; stale_timer/stale_timer_segment/idempotency_conflict/
precondition_required/invalid_event_time/forbidden автоматически не повторяются.
Не заставлять native определять тип ошибки по локализованному тексту error.

`expected` — null для старта при отсутствии таймера либо объект из примера.
При pause/prepare-finish/resume/finish/reset требуется объект; числовые ID положительные.
CAS — проверка в той же транзакции и под той же блокировкой, что изменение:
id, version и начало открытого сегмента должны соответствовать expected.
Нет таймера/другой таймер/другая версия/другой сегмент — 409, без изменения данных.
При start с expected:null требуется отсутствие таймера под блокировкой пользователя.
Offline-очередь не должна автоматически повторять start/resume; это свежие ручные действия.

Каждая изменяющая состояние операция увеличивает существующий version.
Состояние после CAS берётся из БД; версия страницы и taskId не заменяют проверку.
Идентичность сохранять при паузе/продолжении; новая работа после сброса имеет новый id.

## 5. API и время события

Сохранить текущие URL и добавить поля запросов/ответов; новые URL указаны отдельно.
Все записи требуют авторизацию, CSRF, права пользователя и Idempotency-Key.

| Метод и маршрут | Вход и результат |
|---|---|
| GET `/api/time/timer` | Текущий снимок с identity, revision, сегментом и serverNow |
| POST `/api/time/timer/start` | taskId + expected; запуск/продолжение по существующим правилам |
| POST `/api/time/timer/pause` | expected + reason + необязательный at; закрыть только ожидаемый сегмент |
| POST `/api/time/timer/resume` | expected; ручное продолжение с серверного «сейчас» |
| GET `/api/time/timer/proposal` | Существующее предложение + expected для последующей записи |
| POST `/api/time/timer/prepare-finish` | Новый: expected + at; предложение на время события, без записи трудозатрат |
| GET `/api/time/timer/prepared/:requestId` | Новый: сохранённое prepared предложение только своего пользователя |
| POST `/api/time/timer/finish` | expected + rows + note; для prepared также preparedRequestId и cutoffAt |
| DELETE `/api/time/timer` | expected в JSON; сброс только ожидаемого таймера |

В pause время at внутри текущего открытого сегмента закрывает его именно этим временем.
Раньше начала сегмента — 409 `stale_timer_segment`, никогда не подставлять now.
Некорректное/будущее время — 400 `invalid_event_time`, без изменения таймера.
Без at ручная pause использует серверное now. Reason передавать явно:
at сам по себе не означает lock. Не добавлять автоматические resume при восстановлении связи.
serverNow нужен Desktop для приведения времени события к серверной шкале; время доставки
не подменяет время события. Ошибки часов и переход даты в часовом поясе бюро проверить отдельно.

Пример конфликта, который UI показывает пользователю без повторного применения:

```json
{"error":{"code":"stale_timer","message":"Таймер изменён на другом устройстве. Обновите данные."}}
```

Форма error должна соответствовать действующему формату ApiError сервера;
указаны обязательные code/смысл, а не разрешение ломать существующий обработчик ошибок.

## 6. «Закончить» без связи: подготовка, затем проверка человеком

Предлагаемая безопасная семантика prepare-finish: сервер **не пишет строки и не
ставит/снимает паузу**. Он проверяет expected, ограничивает предложение исходным at,
применяет существующие правила округления и возвращает стабильный результат:

```json
{"expected":{"timerId":314,"revision":7,"currentSegmentFrom":"2026-10-27T10:30:00.000Z"},
 "cutoffAt":"2026-10-27T12:00:00.000Z","serverNow":"2026-10-27T12:20:00.000Z",
 "rows":[{"taskId":41,"date":"2026-10-27","from":840,"to":1020}]}
```

Сохранить также текущие поля TimerProposal: task, segments, elapsedSec, today.
Для paused таймера предложение не добавляет работу после последнего закрытого сегмента.
Не заменять captured at временем доставки и не делать повторный proposal «на сейчас».
Страница finish показывает именно prepared предложение и поясняет время окончания.
После ok для prepareFinish native открывает `/desktop/finish?prepare=<requestId>`.
Страница получает сохранённое предложение через GET prepared/:requestId; он известен отправителю.
Поиск и доступ ограничены авторизованными bureau/user, знание requestId не даёт доступа.
Нет/истёкло предложение — ошибка с просьбой проверить данные, без подмены предложением на now.
Таймер до подтверждения сохраняет своё исходное состояние; это явно видно в окне.
«Продолжить работу»/закрытие окна не посылают скрытые pause/resume и ничего не записывают.
«Записать» выполняет CAS по expected и затем всю запись одной транзакцией.
Для finish/reset генерируется новый Idempotency-Key; ключ подготовки используется только
как preparedRequestId. Сервер сверяет его expected/cutoffAt с сохранённой подготовкой.
Ручные изменения rows проверяются существующими правилами, не отменяя CAS.
«Сбросить без записи» требует подтверждения и того же CAS.
Изменение таймера другим ПК после подготовки — 409; старое окно не удаляет новый таймер.

## 7. Идемпотентность и потерянное подтверждение

Использовать срок 24 часа — как у существующего reply; иной срок согласовать явно.
Ключ операции: bureauId + userId + requestId; action входит в хеш payload. Bureau/user
берутся из авторизованного контекста, а не из тела запроса. Origin не является авторизацией;
привязку своей очереди к origin/user обеспечивает Desktop. Пароли/токены не сохранять.
Хранить хеш канонического проверенного payload, код ответа и результат операции.
Одинаковые ключ и payload возвращают сохранённый ответ без повторного изменения.
Тот же ключ с другим payload — 409 `idempotency_conflict`.

Запись результата и изменение таймера/трудозатрат фиксируются атомарно.
Параллельные одинаковые запросы не должны проходить оба; уникальное ограничение в БД.
После авторизации повтор сначала проверяется в журнале операций, затем выполняется CAS:
если результат A уже был записан, replay возвращает его и не трогает текущий B.
Откат транзакции не оставляет успешного результата. Push рассылается после commit.
Детерминированный конфликт повторно не превращается в применение к более новому таймеру.
Очистку просроченных результатов выполнять отдельно; клиент не повторяет автоматически
команды старше объявленного срока. Указать политику хранения ошибок в handback.

## 8. Утреннее уведомление и запуск после 08:00

Существующий timer_stopped остаётся источником истины: midnight/needsCheck не дублировать.
Сейчас живой push уже несёт текст и ссылку на `/time?...`; при позднем запуске есть
только счётчик колокольчика. По idle нельзя восстановить итог остановки.
Предлагается доставка **на каждое устройство**, пока уведомление не прочитано:

- Desktop хранит случайный deviceId UUID локально; это идентификатор доставки, не секрет.
- Новый GET `/api/desktop/timer-notices/pending?deviceId=<uuid>` возвращает свои
  последнее событие timer_stopped, если оно непрочитано и не подтверждено устройством.
  Лимит bootstrap — одно самое новое событие; после ACK/прочтения не выбирать следующее
  старое. Остальная история остаётся в колокольчике, без автоматического ACK/прочтения.
- Новый POST `/api/desktop/timer-notices/ack` принимает `{deviceId,notificationId}`.
  ACK идемпотентен по bureau/user/device/notification, не помечает колокольчик прочитанным.
- Использовать существующий notification.id (Int); не создавать вторую системную новость.
- Добавить необязательную structured delivery в notify: event=`timer_stopped`,
  notificationId; сохранить старые title/text/link/buttons, кнопка остаётся open.
  Метаданные одинаковы для live push и sync; свой deviceId native берёт из локальных настроек.
  Новый Desktop может подписать её «Проверить запись», не разбирая текст заголовка.
- Добавить команду timerNotice: sync(deviceId) / ack(deviceId,notificationId).
  Web делает GET/POST, native хранит локальное состояние показа; main не вызывает API.
- Sync запускается после hello/reconnect и при повторной попытке подавленного показа.
  Политики quiet/focus/inApp сервера и системное DND сохраняются.
  Инициатор sync — только новый native после проверки capability; web не запускает
  исторический replay сам для старого клиента 1.1. Ошибки sync/ACK имеют code/retryable.
  Пока есть подавленный notice, native повторяет sync при снятии запрета и не чаще
  раза в минуту при работающем приложении; только один sync одновременно, без потока popup.
- ACK уходит только после фактического показа. DND/ошибка окна — не ACK, запись остаётся pending.
- Desktop сохраняет shown-ID перед сетевым ACK; повтор ACK/потеря ответа не повторяет popup.
  На другом ПК тот же непрочитанный notice может быть показан один раз для его deviceId.
  Ключ хранения: origin + userId + deviceId + notificationId, общий для live push и sync.

Не обещать математическое exactly-once между UI и БД: crash между показом и локальной
фиксацией может дать повтор. Предложение — предпочесть повтор потере сообщения;
обычные retries и потерянный ACK подавляются сохранённым shown-ID.
ACK-записи удаляются вместе с исходным уведомлением; не вводить отдельный срок вопреки
действующему хранению уведомлений. Чтение в другом клиенте исключает дальнейший pending-показ.

## 9. Миграция и совместимый выпуск

Использовать существующий WorkTimer.version; backfill новых ID сегментов не требуется.
Добавить хранение результатов операций и подтверждений доставки, уникальные ключи,
индексы и очистку. Существующие таймеры/интервалы не переписывать и не округлять заново.
Миграция обратима по данным: завершённые timeEntry и needsCheck сохраняются.

Новый web умеет получать capabilities и добавляет CAS к собственным ручным действиям.
Для нового Desktop сохраняет переданный expected, не подставляет latest после 409.
Для клиента 1.1 без expected допустима только свежая ручная команда без at:
web захватывает свой текущий контекст до запроса и выполняет защищённый API-вызов.
Для finish/reset expected фиксируется из proposal при открытии формы, в том числе
по команде старого Desktop 1.1. На submit нельзя подставлять latest из нового таймера.
Обновление данных/конфликт не пересылает старые строки автоматически; нужен новый явный выбор.
Непривязанные автоматические/отложенные команды с at не воспроизводить.
Старый открытый web без CAS получает 428 `precondition_required` с просьбой обновить
страницу; нельзя молча применить запрос к текущему таймеру. Не повторять запись после refresh.
Выпустить backend/frontend согласованно; capability включать после миграции и всех проверок.
При неизвестной capability новый Desktop сохраняет Д3/Д4, но не включает опасную очередь Д5.

## 10. Приёмка и передача

- [ ] Lock→suspend даёт одну pause исходного сегмента с исходным at.
- [ ] После resume на ПК B старый pause с ПК A получает 409 и не меняет сегменты B.
- [ ] Таймер A закрыт, B запущен: pause/finish/reset со снимком A не меняют B.
- [ ] Старый at никогда не превращается в now; будущий/битый at не изменяет данные.
- [ ] UTC/минуты строк, граница суток и часы клиента согласованы с timeZone/serverNow.
- [ ] Одинаковый ключ+payload, два параллельных запроса и ACK lost дают один результат.
- [ ] Одинаковый ключ+другой payload даёт 409, включая попытку сменить action/identity.
- [ ] Успешный finish A, затем старт B, затем retry finish A не удаляет B и не пишет повторно.
- [ ] Prepared finish сохраняет cutoffAt при повторе, ничего сам не пишет/не паузит.
- [ ] Закрытие/продолжение prepared окна не создаёт скрытых интервалов; stale submit даёт 409.
- [ ] Сохранились округление, нулевые интервалы, слияние и ошибки строк без частичной записи.
- [ ] Полночь/08:00 с выключенным Desktop создают прежние записи; поздний запуск получает pending.
- [ ] DND не подтверждает показ; после его выключения notice доступен, ACK lost не дублирует popup.
- [ ] Bootstrap не показывает старую историю после ACK последнего события; live push и sync не дублируются.
- [ ] Два deviceId разделены; чужие user/bureau/notification недоступны; права и CSRF проверены.
- [ ] Старые Desktop 1.1 сохраняют Д3/Д4; старые web-вкладки безопасно требуют refresh.

Передать: серверную ветку/commit и PR, миграции и порядок выпуска, описание capabilities,
окончательный общий desktop-bridge.ts 1.2 с source commit/blob SHA, примеры запросов/ошибок,
отчёт unit/integration/E2E и результаты двух ПК. Desktop-разработчик отдельно переносит
согласованный shared-файл и включает Д5 только после проверки на стенде.
