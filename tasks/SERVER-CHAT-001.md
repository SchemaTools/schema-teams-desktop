# SERVER-CHAT-001 — что нужно серверу для собственного чата Desktop (макет v4)

Статус: **задание для согласования** ответственным за сервер; реализация не заявлена.
Редакция 2 от 28.10.2026 (редакция 1 от 28.10 — проект со служебной страницей и мостом — отменена, см. раздел 1).
Заказчик результата — разработчик Schema Teams Desktop. Исполнитель — ответственный за сервер Schema Teams.
Исполнитель работает в серверном репозитории и не меняет код Desktop; Desktop не меняет сервер.

## 2. Устройство Desktop-чата (для сведения, сервер это не реализует)

По ТЗ v4, раздел 2.2:

- Вход — обычная страница входа Teams в окне Desktop с постоянным cookie-разделом. Пароль Desktop не видит и не хранит.
- API вызывает **главный процесс** Desktop по cookie `st_session` этого раздела; у изменяющих запросов — заголовок
  `x-csrf-token` из `GET /api/auth/me`. Окно интерфейса само к серверу не ходит.
- Соединение реального времени — **свой клиент Socket.IO в главном процессе** с той же cookie, комната пользователя.
  Для коллег приложение «в сети», как вкладка сайта.
- Сайт Teams в окне не показывается; задачи, доска, объекты открываются на сайте в браузере.
- Мост `desktop-bridge.ts` для чата не нужен. Из общего файла Desktop берёт только `IDEMPOTENCY_*` и `DesktopLatest`.

Отсюда **ограничения для сервера**:

- Не вводить без согласования с Desktop проверку `Origin` / `Referer` и других браузерных признаков на маршрутах
   `/api/auth/*`, `/api/chats*`, `/api/files/*`, `/api/notifications*`, `/api/focus*` и рукопожатии `/socket.io` —
   запросы главного процесса их не несут.
- Не нужны: CORS, доступ по Bearer-токену к чату, новая схема входа, служебная страница, новые команды моста.
- Права, `canWrite`, `canPin`, ответы 401/403/404, `password_change_required` и CSRF остаются как есть.

## 3. Что уже есть — сервер не меняет

По сверке 25.10 сервер даёт почти весь чат макета v4: список чатов с `unread` / `mentioned` / `objectId`,
разговор и участники, страницы сообщений `before` / `after` / `around` по 50, отправку с `replyTo` / `fileIds` / `mentions`
и `Idempotency-Key`, правку и удаление своего, прочтение, загрузку и скачивание файлов, панель вложений, реакции,
закрепление сообщения, поиск в чате, «печатает…», «Фокус» со сводкой, ленту колокольчика с «Прочитать все»,
события `chat:*`, `notification`, `session`. Подробно — `docs/server-api.md`, разделы 1–3.

Служебный чат «Schema Teams» (экран 2) Desktop собирает сам из ленты колокольчика (`NotificationItem`):
отдельный разговор-бот на сервере **не нужен**.

## 4. Что нужно от сервера

Пометки: **[Решение]** — решение руководителя бюро, не менять; **[Предложение]** — устройство можно менять
с записью в `docs/decisions.md` Teams и ответом в этом файле.

### Ч1. Реакции 🔥 и 🎉

**[Решение 25.10]** Добавить в набор сервера. Панель быстрых реакций Desktop: 👍 ❤️ 🔥 ✅ 👀 🎉 и «ещё».
**[Предложение]** В конец `CHAT_REACTIONS` — `fire` 🔥 и `party` 🎉; ничего не убирать (поставленные 😂 и ❓ не теряются);
сайт показывает все восемь.

### Ч2. «Мои задачи на объекте»

**[Решение 25.10]** Чатов отдельных задач и марок нет и не будет: только `direct`, `group`, `object`, `bureau`.
Подписи вроде «КЖ2 · Монолит» на макете — образцы. Новых видов разговоров задание не требует.

**[Предложение]** В `ChatSummary` поле `myActiveTasks: number` — у чата объекта число моих незавершённых альбомов
и подзадач на этом объекте (как в «Моих задачах», без выданных и снятых), у прочих чатов — 0.
Изменилось (назначили, выдали, сняли) — событие `chat:list` этому пользователю. Дополнительно — `objectId` в `MyTaskRow`.

### Ч3. Закрепление чата в списке

**[Предложение]** Своё у каждого пользователя: `PUT /api/chats/:id/top {top: boolean}`, в `ChatSummary` — `top: boolean`;
закреплённые — вверху списка, не больше 5; событие `chat:list` себе. Сайт может показывать так же.

### Ч4. События «Альбом выдан» и «Все замечания закрыты»

Сейчас при выдаче альбома исполнитель уведомления не получает (`subtasks_done` — только проверяющему).

**[Предложение]**
- `album_issued` — исполнителям и проверяющему, когда альбом перешёл в «Выдан», вручную или сам; один раз на выдачу.
- `remarks_closed` — исполнителям альбома, когда закрыто последнее открытое замечание.
- Обе — строки в настройках уведомлений («Альбом выдан», «Все замечания закрыты»), по умолчанию включены;
  `link` — карточка альбома.

### Ч5. Чат «без звука» (не блокирует Desktop 1.0)

Если делать: `PUT /api/chats/:id/mute {until: ISO | null}`, в `ChatSummary` — `muted: boolean`;
сообщения такого чата — без плашки на сайте и без уведомления Windows, счётчик серый.

## Дополнение от 31.10.2026 — повторы загрузки диагностики

Статус: **предложение для ответственного за сервер, не реализовано**. Основные
ответы о Teams 0.12.1 сохраняются. Это дополнение не меняет текущий договор
`support: 1` и не даёт разработчику Desktop разрешения править сервер.

### Наблюдение и граница

На локальной HTTP-фикстуре договора `0.12.1-b` Electron 44.9.1 автоматически
повторил POST после потери ответа. При одной команде интерфейса наблюдались
несколько физических POST с одинаковыми байтами. В финальном `support` одинаковый
ключ сохранил одно сообщение. В `support/files` каждый повтор создал новую
неотправленную запись файла: этот маршрут не идемпотентен.

Проверка выполнялась только на локальном сервере, не на рабочем стенде.
Воспроизведение — [tests/e2e/desktopD7.spec.ts](https://github.com/SchemaTools/schema-teams-desktop/blob/0a79a7741f2ae97f1ee4ebf02c87c87c38d21192/tests/e2e/desktopD7.spec.ts), Desktop 0.9.0: сервер принимает тело,
затем закрывает соединение; потеря ответа сохраняется и для повторных запросов
до явного снятия условия. Desktop не запускает собственный цикл повторов
upload. Он использует в обращении только подтверждённый ID и не угадывает IDs
предыдущих загрузок. Эти ограничения остаются рабочим поведением 0.9.

### Предлагаемый совместимый договор

1. При сохранении всех существующих DTO и маршрутов объявлять `support: 2`
   только после добавления описанной идемпотентности upload. Клиент с минимумом
   `support: 1` продолжает работать; клиент не должен предполагать новый договор
   только по наличию заголовка. Cookie/CSRF и ограничения файлов не меняются.
2. `POST /api/desktop/support/files` принимает необязательный `Idempotency-Key`
   того же ограниченного формата, что финальный POST. Без ключа сохраняется
   прежнее поведение и ответ 201. Ключ загрузки отличается от ключа обращения;
   пространства ключей двух операций независимы.
3. Уникальность — автор + ключ загрузки; запись дополнительно фиксирует чат
   поддержки. Область ограничена бюро/экземпляром сервера; при нескольких бюро
   включить авторитетный bureau scope сессии, не поле от клиента. Другой автор
   или другое бюро не получает чужой файл. Сначала проверяются вход,
   CSRF и действующий настроенный чат: если чат не выбран/удалён, вернуть 409
   `no_support_chat`, не изменяя прежнюю запись. Если действующий чат есть,
   но отличается от закреплённого в ключе, вернуть 409 `idempotency_conflict`,
   не новую загрузку и не перенос старого файла.
4. Запись связывается с нормализованным именем, фактическими размером и SHA256
   входящих байтов. Первый успешный ответ — 201 с текущим `ChatFile`. Повтор
   тех же данных — 200 с **тем же stored file ID и теми же метаданными**.
   Другое имя/размер/содержимое — 409 `idempotency_conflict`, без нового файла
   или pending-вложения. Одного совпадения имени недостаточно.
5. Параллельные одинаковые запросы дают одну видимую запись stored file, одну
   pending-связь и одну закреплённую запись результата. Временные файлы
   проигравших попыток очищаются; сбой не должен возвращать неподтверждённый ID.
   После перезапуска file/pending/idempotency mapping восстанавливаются как
   согласованный набор либо попытка явно блокируется для разбора: новый ID
   под прежним ключом не маскирует неизвестный старый результат. Проверить crash
   между фазами, а не только последовательные HTTP-вызовы. Повтор использованного
   файла не создаёт новый файл и не разрешает присоединение в другое обращение.
6. Срок записи — фиксированные 24 часа от первого успешно закреплённого
   результата (file + pending + mapping), не от прихода/зависания первого запроса
   и не от последнего повтора. После проверки чата и совпадения имени/размера/hash
   утрата файла внутри срока даёт явный 410 `upload_expired`, без создания другого
   файла под прежним ключом. За пределами срока гарантии повтора нет; будущий
   клиент не переиспользует такой ключ.
   Tombstone утраченного файла сохраняется до окончания этого срока, иначе
   раннее удаление mapping позволит повторно создать файл с прежним ключом.
   Очистка idempotency-записей не удаляет файл, уже прикреплённый к сообщению:
   срок хранения вложений остаётся независимым.
7. `no_support_chat`, типы, размер до 50 MiB, octet-stream и CSRF проверяются
   как сейчас. SHA256 вычисляет сервер; заявленный клиентом hash не заменяет
   проверку байтов. Логи не содержат диагностический текст, cookie или байты.

### Приёмка серверной доработки

- Потерянный ответ и несколько физических повторов: одинаковый ID, один файл
  и одна pending-связь; затем одно сообщение финального `support`.
- Параллельные одинаковые запросы дают тот же результат; потерянные/ошибочные
  попытки не возвращают произвольный ID.
- Изменённые байты или имя при прежнем ключе — 409 без нового stored file;
  совпавшее имя при разных байтах не считается повтором.
- Другой автор изолирован; смена/удаление support-чата не переносит файл и не
  обходится прежним ключом.
- Использованный, исчезнувший и просроченный файл имеют явные результаты;
  повтор не продлевает срок. Проверить очистку собственных временных файлов.
- Старый клиент без upload-ключа и все прежние ограничения продолжают работать.

Ответ положить в `tasks/replies/SERVER-CHAT-001.md`: commit/PR, shared-типы,
версия capability, ошибки и результаты тестов. Desktop подключает новый
договор отдельным проверенным изменением после этого ответа. Текущую 0.9
не считать уже использующей новый договор и не блокировать этим дополнением.
