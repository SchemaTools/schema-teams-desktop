# SERVER-PLUGINS-001 — актуальные метаданные известной сборки для Desktop

Дата: 02.11.2026. Статус: **предложение договора, не реализовано и не принято**.
Исполнитель — ответственный за сервер Schema Teams. Desktop-разработчик сервер
не изменяет. Это Д5 Desktop «Плагины»; исторический SERVER-D5-001 относится к таймеру.

## Проблема и фактическое основание

В Teams `0.12.3-a` каталог `GET /api/desktop/plugins` содержит только текущие
stable/beta. Известный старый ID доступен через `GET /api/desktop/plugins/files/:id`,
но этот ответ — ZIP без текущих channel/verified/requires.

[Реализация маршрутов](https://github.com/SchemaTools/schema-teams/blob/0.12.3-a/apps/server/src/modules/plugins/routes.ts),
Git blob `517f64641078bc11716ace2e6a97c1790dfeeeb6`: файл разрешён при отсутствии
revoked и при stable+verified либо beta+tester. Администратор может менять канал,
verified и зависимости без нового ID. Сохранённый channelAtInstall не доказывает
текущий канал. Ответ 200 для tester также не доказывает stable: локальный выбор
«Пробные сборки» может быть выключен.

Desktop уже сохраняет проверенные резервные копии и умеет восстанавливать whole
managed set во временных проверках. Но разрешать активацию скрытого старого build
по историческому каналу или угадывать свежие зависимости нельзя. Пока точных
метаданных нет, неоднозначный откат блокируется с сохранением backup.

## Предлагаемый минимальный договор

Добавить **read-only** `GET /api/desktop/plugins/builds/:id` для одного явно
известного ID. Это предложение нового маршрута, а не описание существующего API.
Не добавлять перечисление истории, admin-доступ или новый способ входа.

Использовать существующую cookie-сессию, авторизацию пользователя и формат ошибок.
Версию возможности `plugins` повысить до 2 после готовности маршрута. Catalog и
file GET версии 1 сохранить совместимыми; старый Desktop продолжает их использовать.

Успешный ответ должен содержать:

- `tester`: актуальное право пользователя в том же согласованном чтении, в котором
  проверяется доступ к этой сборке;
- `pluginCode` и `build`: id, version, **channel** (`stable`/`beta`), verified,
  revit, requires, notes, size, sha256, url, publishedAt; формы существующих полей
  сохранить совместимыми с `DesktopPluginBuild`;
- только метаданные разрешённой, неотозванной сборки действующего плагина.
  Не возвращать storageKey, пути сервера, чужие роли или персональные сведения.

Проверки доступа не слабее file GET: revoked, retired, неподтверждённая stable,
beta без tester, отсутствующий build/файл — недоступность по существующему
соглашению 404. Для отсутствующего входа — существующий отказ авторизации.
Metadata GET не повышает права и не выдаёт вечное разрешение на файл/активацию.

Поля роли, канала, verified, revoked/retired и requires должны относиться к одному
согласованному чтению данных. Не составлять ответ из полей разных версий,
полученных по обе стороны конкурентного admin update. Способ обеспечить это
выбирает серверный исполнитель и описывает в ответе. Если потребуется пакетный
вариант для dependency closure, предложить отдельный ограниченный договор;
не подменять обязательный минимум неограниченной историей.

## Правила интеграции Desktop

Это задание не поручает менять Desktop исполнителю сервера. После ответа клиент:

1. Проверяет capability и читает metadata конкретных known IDs при явном
   rollback/recovery. Никаких придуманных HEAD/Range/admin history запросов.
2. Проверяет текущий канал: beta требует tester и отдельного локального opt-in.
   Старое значение из receipt остаётся историческим фактом.
3. Сопоставляет id/code/version/ZIP size/SHA/годы и требует согласованной полной
   dependency closure по актуальным requires. Неизвестное состояние блокирует
   активацию и сохраняет journal/backup.
4. Независимо проверяет локальные bytes, Windows Authenticode, утверждённого
   издателя и layout. Ответ сервера не заменяет ни подпись, ни publisher pin.
5. Повторяет проверки контекста при отзыве прав/смене сервера/пользователя и перед
   локальной активацией. Metadata response не считается атомарной блокировкой
   будущих серверных изменений; фактические границы свежести фиксируются честно.

При старой capability или отсутствии маршрута остаётся безопасное ограничение.
Не изображать неподдерживаемый исторический откат работающим.

## Серверные проверки и критерии ответа

- Известный старый stable, отсутствующий в latest, возвращает актуальные metadata
  при verified=true и допустимом доступе.
- После stable→beta ответ содержит beta, даже если при установке был stable.
  Tester получает точные данные; non-tester — отказ. Локальный opt-in сервер
  не угадывает и не включает за пользователя.
- После изменения requires без смены ID возвращаются новые значения. Изменённые
  channel/verified/revoked/retired и tester не смешиваются в одном ответе.
- Revoked/unverified stable/retired/missing-file/некорректный ID, отсутствие
  входа и неизвестный ID проверены. Ошибки не раскрывают скрытую историю.
- Catalog/file GET и клиенты capability1 не регрессируют; событие инвалидирования
  каталога и правила доступа остаются совместимыми.
- Ограничения числа/размера зависимостей и валидность DTO проверены серверными тестами.

Результат оформить в `tasks/replies/SERVER-PLUGINS-001.md`: ветка/commit/PR,
точный shared-type и blob SHA, version capability, реальные маршруты/ошибки,
модель согласованного чтения и выполненные тесты. Серверные тесты не заменяют
приёмку Desktop или Revit. Ключи, адреса стенда, установщики и пользовательские
журналы в ответ не добавлять.
