# Клиент 0.7.1: сохранённая автопауза и возвращение

Продолжение S2 после проверенного блока 0.7.0. Серверный договор — Teams
0.12.1-b; серверный код остаётся только для чтения. Реальные команды таймера
и завершение Windows при разработке не выполняются.

До отправки пауза записывается атомарно в локальный outbox. Сохраняются только
хеш сервера, владелец, исходный expected, время события по шкале сервера и ключ
операции. Перезапуск и новое поколение входа не изменяют идентичность команды.
Восстановление требует свежих входа/config/CAS. Таймер B не подставляется
в старую команду A; неподтверждённые и устаревшие периоды остаются для проверки.

Неизвестный сетевой исход допускает повтор прежнего envelope с задержкой:
в одном процессе не больше пяти циклов доставки, между ними не меньше 30 секунд
с увеличением интервала до пяти минут. Каждый цикл допускает один немедленный
сетевой повтор того же запроса, как в 0.7.0. Срок ключа проверяется по свежим часам сервера,
а не по локальному календарю Windows; после 24 часов требуется ручная проверка.
4xx и 5xx автоматически не повторяются. Неизвестный формат ответа также
не считается подтверждением. Полный диск, повреждение файла и отказ записи
показывают предупреждение; очередь не заменяется пустой и не отправляется
как будто сохранение состоялось.

На Windows обработчик BrowserWindow `query-session-end` сохраняет только
кандидат с временем запроса. `session-end` подтверждает его в локальном файле.
Оба обработчика не вызывают API и не препятствуют завершению системы.
Отменённый или оставшийся без финального события кандидат не воспроизводится
после перезапуска; новая блокировка/сон получает своё фактическое время и ключ.
Обработчики устанавливаются один раз и снимаются при уничтожении клиента.
`powerMonitor.shutdown` для Windows не используется.

После подтверждённой паузы сохраняется отдельное намерение показа возвращения;
оно записывается до удаления команды из outbox. Сбой между этими файлами
восстанавливается по одному ключу. Popup предлагается только после свежей
проверки того же приостановленного таймера. «Продолжить» отправляет CAS resume
только после явного нажатия; «Закончить и проверить» открывает существующую
связанную подготовку. Автоматического продолжения нет.

Показ учитывает Фокус, тихие часы, системную политику и настройку «Спросить после
разблокировки». Факт показа записывается только в onShow; после него перезапуск
не создаёт такой же popup. Отказ сохранения показа не выдаётся за устойчивую
однократную доставку. В настройках доступны прежние флажки паузы и вопроса
после разблокировки. Отключение автопаузы оставляет прежнюю очередь для проверки.

Если наблюдалась разблокировка, её граница сохраняется и не сдвигается из-за
ожидания DND. Системное пробуждение и первое подключение после перезапуска
обозначаются отдельно: они не доказывают время фактического возвращения человека.
Пробуждение, пока Windows заблокирована, не завершает период до разблокировки.
Popup содержит период, задачу и подтверждённое отработанное время; отключённый
предпросмотр скрывает детали. Ручное подтверждение проверки может отменить
дальнейший повтор старой паузы, сохраняя текущий серверный таймер.

Автоматические тесты используют отдельные профили, HTTP/Socket.IO фикстуры,
перезапуск и синтетические события. Они не подтверждают доставку настоящих
Windows query/session-end, сон оборудования, полночь и работу двух реальных
устройств. Эти сценарии, исходное проблемное фото из буфера и подпись установщика
остаются отдельной ручной/эксплуатационной проверкой. Полная готовность ТЗ v4
не объявляется; далее продолжаются Д4, Lucide и остальные согласованные этапы.

Покрытие checkpoint: полный предыдущий прогон — 120 Electron-сценариев.
После узких исправлений проверки popup при отложенной системной политике
и защиты старого уничтоженного host повторены типы, линтер, форматирование,
662 модульных и 32 затронутых Electron-теста на окончательном снимке.
Linux CI проверяет типы, линтер и модульные тесты; сквозные Electron-проверки
выполнены локально на Windows.
