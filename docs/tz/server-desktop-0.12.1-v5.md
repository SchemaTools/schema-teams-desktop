## 5. Реестр плагинов Revit (PR-4)

**[Решение 25.10]** Сборки плагинов бюро хранятся в Teams, а не в папке на сервере. Загружают сборки, ставят «проверена» и ведут список испытателей **администратор и BIM-менеджер**. Приложение ставит само только проверенные сборки; пробные — только испытателям с включённым переключателем «Пробные».

Устройство — **[Предложение Claude]**.

### 5.1. Право и данные

- Новое право `plugins_manage` в `PERMISSIONS` (`packages/shared/src/access.ts`) — у ролей «Администратор» и «BIM-менеджер».
- **Плагин:** код (латиница, `floor-plans`), название («Планы этажей»), сокращение для значка (2–3 знака), порядок, «снят» (больше не раздаётся).
- **Сборка:** плагин, версия `X.Y` или `X.Y.Z`, канал `stable` (рабочая) / `beta` (пробная), «проверена» (кто и когда), версии Revit (`[2025, 2026]`), «Что нового» (до 10 000 знаков), файл, размер, `sha256` (считает сервер), зависимости `[{plugin, minVersion}]`, кто загрузил и когда, «отозвана».
- **Испытатели:** список сотрудников; испытатель видит пробные сборки.
- Файлы — в отдельной папке тома данных (рядом с файлами установщика приложения, `apps/server/src/modules/desktop/routes.ts`), не среди вложений задач: в архиве — `.dll`, которые в чат и задачи прикладывать нельзя.

### 5.2. Маршруты для приложения (любой вошедший)

```
GET /api/desktop/plugins
→ { tester: boolean,
    plugins: [{ code, name, short,
                stable: Build | null,    // последняя проверенная рабочая
                beta:   Build | null }]} // последняя пробная — только испытателю
Build = { id, version, verified, revit: number[], notes, size, sha256,
          url: "/api/desktop/plugins/files/<id>", publishedAt, requires: [{plugin, minVersion}] }

GET /api/desktop/plugins/files/:id      файл сборки (zip), только раздаваемой этому пользователю
```

- Неиспытателю пробные сборки не отдаются ни в списке, ни по `files/:id` (404).
- Отозванная сборка не раздаётся; отозвали рабочую — в `stable` предыдущая проверенная.
- Событие сокета `desktop:plugins` (без данных) всем вошедшим — когда сборку проверили, отозвали или изменился список испытателей.
- Подписи `.dll` сервер не проверяет — это делает приложение (ТЗ Desktop 8.3). При загрузке сервер проверяет только, что это zip с `.addin` и `.dll` внутри.

### 5.3. Маршруты управления (право `plugins_manage`)

```
GET    /api/admin/plugins                        плагины со всеми сборками
POST   /api/admin/plugins                        {code, name, short} → плагин
PATCH  /api/admin/plugins/:code                  {name?, short?, order?, retired?}
POST   /api/admin/plugins/:code/builds?version=&channel=&revit=2025,2026
                                                  тело — байты zip, имя — X-File-Name → сборка
PATCH  /api/admin/plugins/builds/:id             {verified?, channel?, notes?, revoked?}
GET    /api/admin/plugins/testers                → PersonRef[]
PUT    /api/admin/plugins/testers                {userIds: number[]}
```

- Предел файла — 200 МБ. Повтор версии в том же плагине и канале — 409.
- Каждое действие — в журнал безопасности (загрузил, проверил, отозвал, изменил испытателей).
- Страница «Плагины Revit» в разделе администрирования сайта: список плагинов и сборок, загрузка, «Проверена ✓», «Отозвать», испытатели. Вид — по дизайн-системе сайта (новый стиль 0.12.0), значки Lucide.

### 5.4. Перенос

Сборки из нынешней папки на сервере администратор или BIM-менеджер загружают в реестр вручную (последняя рабочая каждого плагина, отметка «проверена»). Папку приложение не читает.

## 6. Таймер из приложения через API (PR-5)

**[Решение К7, 29.10]** Таймер управляется из приложения так же, как чат: главный процесс вызывает API таймера по cookie сессии с `x-csrf-token` из `GET /api/auth/me` и заголовком `Idempotency-Key`; мост 1.2 и capability в `hello` **не делаются**. **[Решение 29.10, Д1]** Окна «Выбор задачи» и «Закончить работу» **переносятся в приложение**: их рисует интерфейс приложения по данным API, страницы сайта в окне приложения больше не нужны. Это меняет ТЗ Desktop v4, 2.3. Правила округления, проверки строк и пересечений остаются на сервере: приложение только показывает предложение сервера и отправляет то, что подтвердил человек. Страницы `/desktop/pick` и `/desktop/finish` остаются для старых сборок (договор 1.1) до их вывода.

Основание — задание SERVER-D5-001, переписанное без моста. Проблема (проверено разработчиком Desktop на 0.11.2): `requestId` команды в API не передаётся; отложенная пауза со старым временем может остановить таймер, уже продолженный на другом компьютере (сервер подставляет «сейчас»); старое окно «Закончить» может записать строки таймера A и удалить текущий таймер B.

Места в коде: `apps/server/src/modules/time/timer-routes.ts` (маршруты — стр. ≈124–292), `timer-rules.ts`, `timer-midnight.ts`, модель `WorkTimer` (`id`, `version`) в `prisma/schema.prisma`, `apps/web/src/desktop/timer.ts`, `/desktop/finish`.

### 6.1. Снимок таймера

`GET /api/time/timer` и событие сокета `timer` дополняются полями (прежние не меняются):

```json
{"state":"run","task":{"id":41,"mark":"АР1","title":"Объект А"},
 "startedAt":"2026-10-27T09:00:00.000Z","elapsedSec":10800,"reason":null,
 "timerId":314,"revision":7,"currentSegment":{"from":"2026-10-27T10:30:00.000Z"},
 "pausedAt":null,"serverNow":"2026-10-27T12:00:00.000Z"}
```

- `timerId` — `WorkTimer.id`; `revision` — существующий `WorkTimer.version`, растёт при каждом изменении.
- На паузе `currentSegment: null`, `pausedAt` — конец последнего закрытого сегмента. Нет таймера — все четыре поля `null`.
- Время — UTC ISO с миллисекундами; `serverNow` — всегда, в том числе без таймера.
- После каждого изменения снимок уходит всем компьютерам пользователя.

### 6.2. Ожидаемое состояние

Изменяющие запросы принимают `expected` — каким клиент видел таймер в момент действия:

```json
{"expected":{"timerId":314,"revision":7,"currentSegmentFrom":"2026-10-27T10:30:00.000Z"},
 "at":"2026-10-27T12:00:00.000Z","reason":"lock"}
```

- `start` — `expected: null` означает «таймера нет»; иначе — объект. `pause`, `resume`, `finish`, `DELETE` — объект обязателен.
- Сверка `id`, `version` и начала открытого сегмента — в той же транзакции и под той же блокировкой, что изменение. Не совпало — 409, данные не меняются.
- Коды ошибок (`error.code` в действующем формате ошибок сервера): `stale_timer`, `stale_timer_segment`, `idempotency_conflict`, `precondition_required`, `invalid_event_time`, `forbidden`. Сеть — забота клиента. Текст — в файле строк, например «Таймер изменён на другом устройстве. Обновите данные.».
- Сайт для своих кнопок тоже передаёт `expected`. Старая открытая вкладка без `expected` — 428 `precondition_required` «Обновите страницу»; молча к текущему таймеру не применять.

### 6.3. Время события

- `pause` с `at` внутри открытого сегмента закрывает его именно этим временем. Раньше начала сегмента — 409 `stale_timer_segment`; будущее или некорректное — 400 `invalid_event_time`. Никогда не подставлять «сейчас» вместо переданного `at`.
- `reason` — явно (`lock`, `manual`); `at` сам по себе не означает блокировку.
- Без `at` — серверное «сейчас», как сейчас.
- Автоматического `resume` при восстановлении связи нет — продолжает только человек.

### 6.4. «Закончить работу» без записи вслепую

- Новый `POST /api/time/timer/prepare-finish` `{expected, at}`: проверить `expected`, ограничить предложение временем `at`, применить существующие правила округления; **ничего не записывать и не ставить на паузу**. Ответ — предложение (`rows`, `segments`, `elapsedSec`, `today`) + `expected`, `cutoffAt`, `serverNow`; хранится по `requestId` (ключ из `Idempotency-Key`).
- Новый `GET /api/time/timer/prepared/:requestId` — сохранённое предложение только своего пользователя и бюро.
- Окно «Закончить работу» в приложении показывает именно подготовленное предложение (`GET /api/time/timer/prepared/:requestId`) и время окончания: строки по задачам, округление, предупреждения сервера (пересечения, «проверить»). Человек может поправить строки в пределах правил; каждое изменение проверяет сервер — `POST /api/time/timer/validate-rows` `{preparedRequestId, rows}` возвращает ошибки по строкам и итог без записи. Нет или истекло — «Проверьте данные», без подмены предложением «на сейчас».
- «Записать» — `finish` с новым ключом, `expected`, строками и `preparedRequestId`; сервер сверяет с подготовкой и пишет одной транзакцией. Изменение таймера на другом компьютере после подготовки — 409.
- «Продолжить работу» и закрытие окна ничего не пишут и скрытых пауз не ставят. «Сбросить без записи» — с подтверждением и той же сверкой.

### 6.4а. «Выбор задачи» в приложении (Д1)

- Новый `GET /api/time/timer/pick-list` — то, что сейчас собирает страница `/desktop/pick`: мои активные альбомы и подзадачи, последние задачи таймера, личные задачи, поиск по шифру и названию (`?q=`). Те же права и видимость, что у страницы (модуль `access`). Если данные страница уже берёт из API — вынести без изменения правил и указать в PR.
- Старт таймера из окна — `start` с `expected` и `Idempotency-Key` (п. 6.2, 6.5).
- Вид окон — по макету Desktop; если в макете v4 их нет — разработчик Desktop делает макет на согласование руководителю до кода.

### 6.5. Идемпотентность

- Все изменяющие запросы таймера — с `Idempotency-Key` (как у отправки сообщения, `chat/routes.ts`, стр. ≈835). Ключ операции — бюро + пользователь (из сессии) + ключ; хранится хеш проверенного запроса, код и результат ответа, 24 часа.
- Тот же ключ и тот же запрос — сохранённый ответ без повторного изменения; тот же ключ и другой запрос — 409 `idempotency_conflict`. Параллельные одинаковые — проходит один (уникальное ограничение в базе).
- Запись результата и изменение таймера — в одной транзакции; событие сокета — после фиксации.

### 6.6. Уведомление «Таймер остановлен в полночь»

Существующее `timer_stopped` остаётся источником; полночь и пометку «проверить» не дублировать. Приложение, запущенное после 08:00, сейчас видит только счётчик колокольчика.

- `GET /api/desktop/timer-notices/pending?deviceId=<uuid>` — последнее непрочитанное `timer_stopped` этого пользователя, не подтверждённое этим устройством (одно, самое новое).
- `POST /api/desktop/timer-notices/ack` `{deviceId, notificationId}` — идемпотентно; колокольчик прочитанным не помечает.
- `deviceId` — случайный идентификатор, хранится в приложении; не секрет и не авторизация.
- В событии `notification` — `kind: "timer_stopped"` и `notificationId` (см. 2.4), чтобы приложение подписало кнопку «Проверить запись ↗», не разбирая текст.
- Подтверждения удаляются вместе с уведомлением.

### 6.7. Выпуск

- Старые сборки приложения (договор моста 1.1) продолжают работать: свежая ручная команда без `at` — как сейчас; отложенные команды с `at` без `expected` не применяются.
- Существующие таймеры и записи трудозатрат не переписываются и не округляются заново.

## Приёмка

1. Реакции 🔥 и 🎉 ставятся и снимаются, событие `chat:reaction` приходит; старые на месте, сайт показывает восемь.
2. Чат объекта: назначили задачу — `myActiveTasks` вырос, пришёл `chat:list`; выдали — уменьшился; у прочих чатов — 0. `MyTaskRow` содержит `objectId`.
3. Закреплённый чат — вверху у себя, у коллег без изменений; шестой — понятная ошибка.
4. Альбом выдан — `album_issued` исполнителям и проверяющему один раз; последнее замечание закрыто — `remarks_closed`; выключено в настройках — не приходит.
5. Тихие часы включены — `chat:message` получателю приходит с `quiet: true`, вне тихих часов — `false`; `GET /api/desktop/config` отдаёт пояс, конец дня, `serverNow`, чат поддержки и только проверенные `capabilities`.
6. `GET /api/desktop/morning` в выходной — `workday: false`; новое замечание к моему альбому — `newRemarks` +1.
7. Чат поддержки выбран — сообщение с файлами из приложения доходит от имени отправителя; не выбран — 409.
8. Администратор и BIM-менеджер загружают сборку и отмечают «проверена»; без `plugins_manage` — 403 на маршрутах управления.
9. `GET /api/desktop/plugins` у неиспытателя — без пробных, у испытателя — с пробными; пробная сборка неиспытателю — 404; `sha256` совпадает с файлом; отозванная не раздаётся; `desktop:plugins` приходит после проверки и отзыва.
10. Таймер: блокировка → одна пауза исходного сегмента с исходным временем; после `resume` на втором компьютере старая пауза с первого — 409 без изменений; старое `at` никогда не превращается в «сейчас».
11. Таймер A закрыт, B запущен: `pause` / `finish` / сброс со снимком A не меняют B; повтор `finish` A после старта B не удаляет B и не пишет повторно.
12. Одинаковый ключ и запрос, два параллельных запроса, потерянный ответ — один результат; тот же ключ с другим запросом — 409.
13. Подготовка «Закончить» сохраняет `cutoffAt`, ничего не пишет и не ставит на паузу; закрытие окна не создаёт скрытых интервалов; `validate-rows` возвращает ошибки по строкам и ничего не пишет; `pick-list` отдаёт те же задачи, что страница `/desktop/pick`, с учётом прав.
14. Полночь при выключенном приложении — прежняя запись с пометкой; поздний запуск получает `pending`; подтверждение с одного устройства не скрывает уведомление на втором.
15. Старая вкладка сайта без `expected` — 428 «Обновите страницу»; старая сборка приложения 1.1 работает как раньше.
16. Запросы без `Origin` с cookie и CSRF и Socket.IO с cookie работают (тест раздела 7). Модульные тесты на права, каналы раздачи, новые события и таймер; журнал без текстов сообщений.
