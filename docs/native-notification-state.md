# Проверка системного подавления уведомлений

`native/NotificationState.cs` — собственный helper .NET Framework 4.x без внешних
библиотек. При запуске он читает два независимых состояния и печатает одну строку:

```json
{"v":1,"shell":5,"focus":0}
```

- `shell`: результат документированного
  [SHQueryUserNotificationState](https://learn.microsoft.com/windows/win32/api/shellapi/nf-shellapi-shqueryusernotificationstate),
  значения 1–7. Значение 5 — QUNS_ACCEPTS_NOTIFICATIONS. Ошибка — null.
- `focus`: активный профиль Focus Assist из
  WNF_SHEL_QUIETHOURS_ACTIVE_PROFILE_CHANGED. 0 — выключен, 1 — только приоритетные,
  2 — только будильники. Ошибка, размер не DWORD или неизвестное значение — null.
- `v`: версия локального формата вывода. Старый одиночный результат `5` не доказывает,
  что Focus Assist выключен, и не должен разрешать показ.

Строка собирается только из фиксированных ключей, чисел и null. Никаких путей,
идентификаторов пользователя, сообщений или текстов исключений в выводе нет.
Helper не принимает аргументы, не изменяет системные параметры и не вызывает
NtUpdateWnfStateData. Запросы не зависят друг от друга: даже при ошибке Shell API
состояние Focus Assist читается отдельно.

## Почему двух запросов достаточно для решения о показе

Приложение может разрешить собственное окно и звук только при `shell = 5` **и**
`focus = 0`. Во всех остальных случаях оно должно сохранить непрочитанное, но
подавить окно и звук. В частности, неизвестное состояние не приравнивается к
выключенному Focus Assist.

Shell API описывает презентацию, полный экран, блокировку и quiet time. Его
[QUNS_QUIET_TIME](https://learn.microsoft.com/windows/win32/api/shellapi/ne-shellapi-query_user_notification_state)
означает период после первого входа/обновления Windows и сам по себе не подтверждает
современное «Не беспокоить». Поэтому для профиля требуется отдельный запрос.

## Источник способа чтения и лицензия

Для выбора идентификатора WNF и ABI использована реализация
[windows-focus-assist, commit 042e154d20224517bac512462f776bdaa667d9e9](https://github.com/bitdisaster/windows-focus-assist/blob/042e154d20224517bac512462f776bdaa667d9e9/lib/focus-assist.cc),
лицензия [MIT](https://github.com/bitdisaster/windows-focus-assist/blob/042e154d20224517bac512462f776bdaa667d9e9/LICENSE).
Node-модуль и его код COM в приложение не добавляются. C#-обвязка, проверка размера,
значений и формат вывода написаны в настольном репозитории. В исходном модуле
проверка диапазона содержит `>= 0 || <= 2`; она здесь не используется.

Тот же WNF-запрос встречается в C#-приложении для Windows 11 23H2+:
[SpaceNotch, commit 0ff6f1fb3ebf86a53af78c60bdc2e0746c4d6929](https://github.com/nicoo-o/SpaceNotch/blob/0ff6f1fb3ebf86a53af78c60bdc2e0746c4d6929/src/SpaceNotch.Platform.Windows/Notifications/FocusAssistProbe.cs).
Это дополнительное свидетельство применения, а не проверка нашего приложения на
Windows 11.

## Ограничения и ручная проверка

**WNF — недокументированный и не гарантированный Microsoft API.** Его имя, ABI и
профиль могут измениться при обновлении Windows. Если чтение перестанет работать,
приложение должно подавить собственный UI при неизвестном состоянии, а не считать
режим выключенным. Другой официальный универсальный API для режима Focus Assist
Windows 10 в проверенных материалах не найден.

Документированный
[FocusSessionManager](https://learn.microsoft.com/windows/apps/windows-app-sdk/applifecycle/focus-session)
описывает сеансы Focus в Windows 11; он не является заменой чтения ручного
Focus Assist на Windows 10.

Проверка на целевой ОС: прочитать результат при выключенном режиме, затем при
«Только приоритетные» и «Только будильники», сопоставить `focus = 0/1/2` с UI
Windows, проверить отсутствие собственного окна **и** звука и сохранение счётчика.
После выключения режима новое сообщение должно снова показываться; старые
подавленные сообщения не повторяются. Состояние Windows после проверки следует
вернуть к исходному. Проверки Windows 10 и Windows 11 фиксируются раздельно;
наличие кода для обеих ОС не считается успешной ручной проверкой.
